**Scope.** The recurring work of keeping this repository correct, the nine maintenance scripts in
`scripts/`, the two of them that are **broken today**, and a symptom → cause → fix table for the
failures that actually occur in this environment.

[`docs/DEVELOPMENT.md`](DEVELOPMENT.md) (contributor setup) and

## 1. What "maintenance" means in this repository

This is a **static, client-only application with no server, no database and no deployment
pipeline** (`PROJECT_CONTEXT.md` §13.2: deployment is "Not found in codebase"). There is therefore
exactly one kind of maintenance that can go wrong: **the committed artefacts drift away from the
source they are generated from.**

The repository has four generated artefacts, and three of them are checked in:

| Generated artefact | Source of truth | Regenerated by | Committed? |
|---|---|---|---|
| `src/schema/columns-vhsnd.ts` | `data/vhsnd-columns.csv` | `node scripts/gen-columns.mjs` | Yes |
| `src/export/templates.generated.ts` | `templates/*/**.docx`, `templates/*/**.pptx` | `npm run embed:templates` | Yes |
| `templates/default/vhsnd-letter.docx` | built by a script | `npm run embed:templates` (first half) | Yes |
| `sample-data/vhsnd-sample.xlsx` | `data/vhsnd-columns.csv` + `scripts/make-sample-data.cjs` | `npm run make:sample` — **currently broken, §4.1** | Yes |
| `sample-data/DATA_EX_SHAPE.csv` | a real export + `scripts/make-shape-sample.mjs` | `node scripts/make-shape-sample.mjs <input.csv>` — **has a hard-coded default path, §4.2** | Yes |

> The rule from `docs/DEVELOPMENT.md:130` applies without exception: **never edit these by hand.**
> Edit the source, regenerate, commit **both** the source and the output.

## 2. The recurring tasks

### 2.1 Regenerate the column registry

**Trigger:** the official VHSND form gains, loses or renames a column.

```bash
node scripts/gen-columns.mjs
```

`scripts/gen-columns.mjs:9-10` reads `data/vhsnd-columns.csv` and writes
`src/schema/columns-vhsnd.ts`. The script:

- parses `label,code` lines with quoted-label support (`:15-48`);
- skips rows with an empty code, with a warning (`:53-56`);
- keeps the **first** label seen for a duplicate code (`:57-59`);
- sorts by code with a numeric collation (`:63`) — so the generated file's order does **not** match
  the CSV's order;
- emits `VHSND_COLUMNS`, `VHSND_COLUMN_MAP` and `columnLabel()` (`:65-79`).

**There is no npm script for this** — it must be run manually. That is deliberate (the file is
"do not hand-edit" and only changes with the form), but it is a footgun: nothing in CI reminds you.
See [`20-future-improvements.md`](20-future-improvements.md) §4.

**After regenerating, check the counts.** `tests/schema/columns.test.ts` pins the registry size, the
uniqueness of rule ids and the shape of each code, so a change to the CSV will fail the test suite
until the expectation is updated in the same commit (`docs/DEVELOPMENT.md:208`).

### 2.2 Regenerate the DOCX template embedding

**Trigger:** a district's official letterhead is supplied, or the generic template changes.

```bash
npm run embed:templates
```

That npm script chains **two** commands (`package.json:14`):

```json
"embed:templates": "node scripts/make-default-templates.mjs && node scripts/embed-templates.mjs"
```

1. **`scripts/make-default-templates.mjs`** builds a minimal, valid `.docx` from scratch using
   `JSZip` (`:17`, `:105-115`), writing `templates/default/vhsnd-letter.docx`. It hand-writes the
   OOXML parts: `[Content_Types].xml` (`:87-88`), `_rels/.rels` (`:90-91`),
   `word/document.xml` (`:69-85`), `word/_rels/document.xml.rels` (`:93-94`),
   `word/styles.xml` (`:96-97`) and the two `docProps` parts (`:99-103`). The placeholders it
   writes are listed at `:29-67` and are the contract the Report screen depends on:
   `{{dataset.name}}`, `{{summary.*}}`, `{{FOR chart IN charts}}`,
   `{{IMAGE chartImage($chart.blobKey)}}`, `{{FOR indicator IN indicators}}`,
   `{{FOR a IN audit}}` and `{{manifest}}`.

   **Caution:** this script **overwrites** `templates/default/vhsnd-letter.docx`. If a real
   district template has been dropped into `templates/`, do not run the first half — run
   `node scripts/embed-templates.mjs` on its own.

2. **`scripts/embed-templates.mjs`** scans `templates/` for `.docx`/`.pptx` (`:16-29`), base64s each
   one (`:32-36`) and writes `src/export/templates.generated.ts` with a `templates` array and a
   `getTemplate(rel)` helper (`:42-51`). If nothing is found it warns and emits an **empty
   registry** (`:38-40`) — which is the state that disables the DOCX export button.

**Why this matters:** the app never fetches its template; it reads the embedded copy at
`src/app/report/page.tsx:11,55`. If you edit a template and forget to re-run the embed step, the
export silently keeps using the old bytes. See §5.4.

### 2.3 Regenerate the fixtures

```bash
npm run make:sample                                   # BROKEN today — see §4.1
node scripts/make-shape-sample.mjs path\to\DATA_EX.csv # see §4.2 for the default-path trap
```

`sample-data/vhsnd-sample.xlsx` is a **fully synthetic** 160-row workbook with a seeded PRNG
(`mulberry32(20260714)`, `scripts/make-sample-data.cjs:49-59`) and nine deliberately contradictory
rows planted at indices 4, 6, 8, 10, 12, 14, 16, 18 and 20 (`:114-123`). It is the fixture the
Review/Visualise/Report screens are demoed with, and `tests/sample-data.test.ts` asserts against it.

`sample-data/DATA_EX_SHAPE.csv` is a **pseudonymised twin of a real export**: it preserves the
two-row header, the full 252-column spread, the space-delimited select-multiple parents and the
value shapes that historically broke coercion, and replaces names with `ANM One` / `ANM Two` /
`ANM Three` (`scripts/make-shape-sample.mjs:17-24`). The pseudonym map is hard-coded, so a *new*
real export may need that map extended before the fixture is safe to commit.

### 2.4 Run the gates

Five gates, all of which must be green before committing (`docs/DEVELOPMENT.md:66-80`):

| # | Gate | npm | Direct `node` (works with `&` in the path) | Passes when |
|---|---|---|---|---|
| 1 | Types | `npm run typecheck` | `node .\node_modules\typescript\lib\tsc.js --noEmit` | zero errors |
| 2 | Lint | `npm run lint` | `node .\node_modules\eslint\bin\eslint.js .` | zero warnings/errors |
| 3 | Tests | `npm run test` | `node .\node_modules\vitest\vitest.mjs run` | 19 files / 212 tests pass |
| 4 | Build | `npm run build` | `node .\node_modules\next\dist\bin\next build` | `out/` written, 6 routes |
| 5 | Offline | `npm run build:check-offline` | `node scripts/check-offline.mjs` | no remote references in `out/` |

`npm run ci` chains gates 1–4 (`package.json:18`) and **does not include gate 5**.
`npm run build:all` chains build → check-offline → embed:templates (`package.json:17`) and is the
correct command before shipping.

**Two things the gates will not catch, on their own:**

- Gate 4 **wipes `out/`**, including the `out/dev` scratch directory the dev server keeps its
  manifests in. Restart `next dev` after any build — see §5.1.
- `next dev` / `next build` rewrite the `nextjs-agent-rules` block in `AGENTS.md`. **Commit that
  block with your work**; deleting it just re-creates the uncommitted change
  (`PROJECT_CONTEXT.md` §11.7).

## 4. Known-broken tooling — two defects, stated plainly

### 4.1 Defect D1 — `npm run make:sample` fails: ESM syntax in a `.cjs` file

`scripts/make-sample-data.cjs` uses ES module syntax in a CommonJS file:

```js
10: import { readFileSync, mkdirSync } from "node:fs";
11: import { resolve, dirname } from "node:path";
12: import XLSX from "xlsx";
```

Node parses a `.cjs` file as CommonJS regardless of the nearest `package.json`, and `package.json`
does **not** set `"type": "module"` (there is no `type` field at all — `package.json:1-47`). The
result, confirmed by running `node --check scripts/make-sample-data.cjs` in this repository:

```
scripts/make-sample-data.cjs:10
import { readFileSync, mkdirSync } from "node:fs";
^^^^^^
SyntaxError: Cannot use import statement outside a module
```

**Impact.** The documented way to regenerate the demo fixture does not work. The *committed*
`sample-data/vhsnd-sample.xlsx` is up to date, so nothing is blocked today — but the next person
who needs to change the sample data will hit this immediately.

**This is not a stylistic nit.** `eslint.config.mjs:8-15` contains a carve-out that disables
`@typescript-eslint/no-require-imports` for `**/*.cjs`, with the comment "Node maintenance scripts
are CommonJS by extension (.cjs), so `require` is the only way for them to load a module." The lint
config therefore *asserts* that `.cjs` files use `require`; the file violates that contract and the
lint rule does not catch it because the rule is disabled for exactly this extension.

**Fix approach (recommended).** Convert the file to CommonJS, matching the sibling scripts
`diagnose-workbook.cjs` and `debug-raw.cjs`:

```js
// scripts/make-sample-data.cjs
const { readFileSync, mkdirSync } = require("node:fs");
const { resolve, dirname } = require("node:path");
const XLSX = require("xlsx");
```

No other change is required: the rest of the file (`:17-134`) is already plain JavaScript with no
ESM-only features — no top-level `await`, no `import.meta`, no `export`.

**Alternative.** Rename the file to `scripts/make-sample-data.mjs` and update
`package.json:15` to `"make:sample": "node scripts/make-sample-data.mjs"`. This keeps the modern
`import` syntax but leaves the `.cjs` scripts inconsistent with each other and requires updating
`docs/PIPELINE.md` §7.4, `docs/DEVELOPMENT.md` and `PROJECT_CONTEXT.md` §12.4.

**Recommendation:** the CommonJS conversion. It is the smaller diff, it matches the lint carve-out,
and it matches the two working `.cjs` diagnostics scripts.

### 4.2 Defect D2 — `scripts/make-shape-sample.mjs` hard-codes another machine's path

```js
14: const SRC = resolve(process.argv[2] ?? "C:/Users/DADITYA/Downloads/DATA_EX.csv");
```

When no argument is supplied, the script reads from an absolute path on a specific person's
machine. On any other checkout this throws `ENOENT: no such file or directory` — and because the
input is a *real export* containing respondent names, the hard-coded path is also a small privacy
smell: it names a user's home directory inside a tracked source file.

**Impact.** The script only works when an explicit input path is passed, or on the machine the
default was written for.

**Fix approach.**

```js
const arg = process.argv[2];
if (!arg) {
  console.error(
    "Usage: node scripts/make-shape-sample.mjs <path-to-real-export.csv>\n" +
    "The source must be a real ODK/VHSND CSV export. Review the PSEUDONYMS map in this\n" +
    "script before committing the output: any name not in the map is replaced with\n" +
    "'Worker <index>'.",
  );
  process.exit(1);
}
const SRC = resolve(arg);
```

The explicit usage message matters: the pseudonym map (`:17-24`) only covers **five** names.
Any other name in the input becomes `Worker ${i}` (`:61`) — safe, but it means the fixture will
contain placeholders unless the map is extended. That is a deliberate, documented design, but it
should be stated at the point of failure rather than discovered later.

If the registry is still empty afterwards, `scripts/embed-templates.mjs:38-40` found no `.docx`/`.pptx` under `templates/` — check the file layout (`templates/<dir>/<file>.docx` is the shape the scanner expects, `:20-24`). |

### 5.4 Local storage and data loss

| Symptom | Cause | Fix |
|---|---|---|
| **Data disappeared after clearing site data / browser storage** | **The encryption key was destroyed too.** The AES-256-GCM key is generated on first use and stored as raw bytes in a *separate* IndexedDB database, `pipeline-crypto` (`src/lib/crypto.ts:3-4,61-82`). Clearing site data deletes that database along with `vhsnd-pipeline`, so every encrypted record becomes undecryptable. | **There is no recovery.** No passphrase, no key export, no backup path (`PROJECT_CONTEXT.md` §14.4). Re-import the source file and redo the review decisions. The app *does* warn before its own wipe ("This cannot be undone.", `src/app/report/page.tsx:130`) and its "Erase all local data" button is the only in-app deletion path (`src/lib/storage/idb.ts:260-273`). |
| The app cannot decrypt an existing dataset after an update | The key is bound to the **origin** (scheme + host + port). Serving the same `out/` folder from `localhost:3000` and then from `https://example.org` gives two different origins, hence two different keys. | Use one origin consistently. Moving data between machines/origins is currently impossible — see [`20-future-improvements.md`](20-future-improvements.md) §2. |
| The landing page shows no datasets although one was imported | The dataset list comes from `listDatasets()`, which decrypts every stored snapshot (`src/lib/storage/idb.ts:99-117`). If any snapshot fails to decrypt, the whole call throws and the page renders an empty list. | Reload. If it persists, the key is gone (previous row) or the database is corrupt; re-import. |
| "Dataset not found in local storage." (`src/stores/datasetStore.ts:64`) | The `activeDatasetId` in the persisted workflow store points at a dataset that no longer exists — for example after the ingest screen deleted a superseded dataset (`src/app/ingest/page.tsx:132`). | Pick a dataset from the landing page. |

## 6. The Windows `&`-in-path shell workaround

This repository's own folder is named `PIPELINE-FOR-VHSND&PMSMA`. In `cmd`, npm's `.bin` shim
generation splits the path at the `&`, so every command that resolves a local binary fails with a
message like:

```
'PMSMA\node_modules\.bin\' is not recognized as an internal or external command.
Cannot find module 'C:\Users\...\Downloads\typescript\bin\tsc'
```

This affects `npx <pkg>`, `npm run lint`, `npm test`, `npm run typecheck` and `npm run build`.

**Two workarounds.**

1. **Clone to a path without `&`** — preferred; it fixes everything at once.
2. **Call the entry points through `node` directly.** In PowerShell:

```powershell
node .\node_modules\typescript\lib\tsc.js --noEmit
node .\node_modules\eslint\bin\eslint.js .
node .\node_modules\vitest\vitest.mjs run
node .\node_modules\next\dist\bin\next build
node scripts\check-offline.mjs
```

Note that `docs/DEVELOPMENT.md:55` gives the `typescript/lib/tsc.js` path while
`PROJECT_CONTEXT.md:999` and `docs/PIPELINE.md:422` give `typescript/bin/tsc`. Both exist in the
installed package; the `lib/tsc.js` form is the safer one on Windows because it is the actual
entry point rather than a sibling shim.

Scripts that already shell out to `node scripts/*.mjs` — for example `npm run build:check-offline`
(`package.json:16`) and `npm run embed:templates` (`:14`) — work in both cases.

**PowerShell 5.1 note:** avoid `&&` between commands; use `;` or `if ($?)`
(`docs/PIPELINE.md:418`).

## 7. A short diagnostics playbook

When an import misbehaves, work down this list — it is ordered cheapest-first.

| Step | Command | What it tells you |
|---|---|---|
| 1 | `node scripts/debug-raw.cjs path\to\export.xlsx` | The literal first four rows of every sheet. Are there one, two or three header rows? Is row 3 a code row? |
| 2 | `node scripts/diagnose-workbook.mjs path\to\export.xlsx` | How many headers are recognised codes, how many are case-variants, how many are unknown. Plus samples of the watched columns. |
| 3 | `node scripts/diagnose-workbook.cjs path\to\export.xlsx` | The same, through the CommonJS path — use this one if the `.mjs` variant misbehaves on your Node version. |
| 4 | `node scripts/gen-columns.mjs` | Regenerates the registry — run it if step 2 reports many unknown headers; the CSV may simply be out of date. |
| 5 | `npm run test` | 212 assertions across 19 files, including the header-resolution ladder and the `H13` guard. A failure here is the fastest pointer to the cause. |
